## Learned User Preferences

- Keep `just` recipes minimal: `just build`, `just test`, `just run`, `just stop`, and `just reset` per app (`backend` or `mobile`), plus root variants, `just install` (clone setup), `just encrypt`, `just decrypt`, `just show-env` (dotenvx on `.env.local`; encrypt/decrypt also touch `.env.production` when present; show-env is `.env.local` only via `with-dotenv-local.sh`), and `just relayer balance` (fee payer pubkey + mainnet SOL via `go run -C apps/backend ./cmd/print-relayer-pubkey`). `just reset` = stop all + wipe local Postgres; `just reset db` = DB only. `just killports` kills API listeners (8080), not Compose Postgres (54322). `just stop mobile` and full `just reset` uninstall `com.monaco.app` on every available sim to clear Privy session (`scripts/stop-mobile.sh`).
- When the user says "test mobile" or runs `just test mobile`, run host `swift test` in `packages/mobile-core` (fast, deterministic; no iOS Simulator or `xcodebuild test`). `just build mobile` / `just run mobile` / `scripts/ios-build` / `./scripts/ios-sim` use `scripts/resolve-ios-sim.sh` (SimSlim when ready, else stock sim with stderr warning). Do not boot a sim for unit tests. Never commit a UDID. Never `simctl erase`. Agent tap-through may use `.cursor/skills/ios-simslim-fast-qa/SKILL.md` or XcodeBuildMCP with `--simulator-id` from `scripts/gold-sim-udid.sh` (fail-loud if `SIMSLIM_UDID` is unset; not used by human `just run`). Do not drive taps with AppleScript, CGEvent, or coordinate hacks. For `just test backend`, use stubs/mocks only—never hit the live Jupiter API; trim property tests that run longer than ~2 minutes.
- App directories are `apps/backend` and `apps/mobile` by intentional rename; do not refer to or recreate `apps/api` or `apps/ios`. The iOS Xcode project/scheme may stay named `Monaco` under `apps/mobile`.
- For M1 testing, support email OTP login in addition to SMS auth.
- Use dotenvx for repo secrets (`.env.local` for dev, `.env.production` for prod). Teammates share encrypted `.env.local` plus `.env.keys` in the clone root (gitignored). Backend `just run` / `just test backend` re-exec under `scripts/with-dotenv-local.sh`. Mobile Privy: `ensure-ios-privy-config.sh` → xcconfig; `with-ios-privy-env.sh` / `./scripts/ios-sim` → `SIMCTL_CHILD_*` at simctl launch only (relaunch from sim home icon drops creds). iOS scripts require `PRIVY_APP_CLIENT_ID` from decrypted `.env.local`—legacy `PRIVY_AUTH_ID` in plain `.env` must not substitute. Justfile `dotenv-load` only reads plain `.env`. Repo onboarding must be machine-agnostic—another dev clones, decrypts, and runs the same way; prune machine-specific docs or commands.
- GitHub issue and milestone ticket bodies should follow the write-ticket format (Context, Problem, Proposal with Implement exactly, acceptance criteria, verification commands, Done when) with minimal agent discretion.
- Parallel milestone implementation should use worktree-orchestrate with Composer 2.5 subagents unless another model is explicitly requested; run unrelated tickets in parallel in separate git worktrees (one lane per feat branch), not serialized on one checkout; split mobile vs backend tickets to separate agents; parent orchestrator owns the queue and must not spawn nested orchestrator subagents; when multiple agents overlap on one task, keep whichever is furthest along only.
- Ticket/feature work runs in git worktrees under `.worktrees/`; never dirty the user's primary checkout (often `main`)—land on named integration branches in the worktree, not by checking out the primary tree; subagents must cd and use absolute paths inside the worktree because Task inherits parent cwd. After landing, remove the worktree and put primary on the named branch with a clean tree matching HEAD so the user can build/test from repo root via `git checkout <branch>`—do not leave work only in `.worktrees/` or let primary disk revert the branch.
- For Privy dashboard verification or client settings during agent QA, use the attached Privy browser tab; do not ask the user to make dashboard changes. Prefer Privy API/dashboard ops over ad-hoc product PATCH-in-loop for legacy wallet signer fixes.
- Never skip verification steps (ticket Done-when, milestone manual verification, `just test`/`just build`, gold-sim QA) unless the user explicitly says to skip in the current message.
- When the user says they'll build or run themselves, verify code changes only and skip sim, build, or run in that session unless they ask in the current message.
- Product UI: prefer toasts over main-UI popups or banners for action confirmations; never hyphenate wallet addresses; show human-readable stock names or symbols, not raw mint addresses or "xStock" branding. User-facing copy uses "cabal" (not club/group); API routes and types stay `groups`. Use "deposit" for inbound USDC to platform balance; "fund this cabal" for sweeping platform USDC into a group treasury; partial cabal stake sales use a sell flow without leaving the group.

## Learned Workspace Facts

- Monaco is a mobile app for group treasury investing in tokenized stocks (xStock via Jupiter swaps). Apps live at `apps/backend` (Go API) and `apps/mobile` (Swift/iOS). Host-runnable Swift unit tests live in `packages/mobile-core`. README is clone/run/how-to only; product and ops details live under `docs/` (e.g. `docs/product.md`, `docs/ops-sweep-wallets.md`). The existing Groups tab lists all groups (joined and unjoined)—not a separate bottom-nav groups feature.
- Go and Swift integrate via HTTP API contract only; mobile never calls xStocks, Jupiter, Pyth Hermes, or Solana RPC for product flows (plus Privy Swift for auth/wallets). Group detail uses `GET /v1/groups/{id}/view` (pot, member board, treasury address).
- Local development database is Docker Compose Postgres; do not use hosted or production Supabase for local testing. App `DATABASE_URL` is `monaco`; `just test backend` / Go tests auto-use sibling `monaco_test` (derived, no extra env).
- Privy handles auth and per-user wallets; one Privy wallet per user—reuse existing wallet on login, never recreate. OTP sendCode (SMS/email) is Privy-direct to auth.privy.io; Monaco backend only after `POST /v1/auth/session`—no API traffic during OTP is expected. Inbound USDC stays in the member Privy wallet as platform balance; platform balance shown to users is on-chain USDC (`MemberUSDCBalance`) minus in-flight fund-to-cabal intents—not ledger-only. User-initiated fund-to-cabal sweeps an exact amount from member wallet to group treasury. Deposit UI shows the user's copiable Privy deposit address; no in-app amount submit on deposit. For local dev/testing, USDC sent from the developer's own Phantom wallet to that deposit address is picked up by the backend poller without agent MCP. No `FAKE*` wallet address rows in local DB—they break the deposit poller.
- Leaderboard and P&L (within a group and across groups) are core product focus, with portfolio views and partial USDC redeem. Group member board lists every `group_member` regardless of deposit or P&L. Transaction history includes group buys and sells plus pending and failed states.
- `PHANTOM_APP_ID` belongs in Cursor Phantom MCP config, not Monaco `.env` — Phantom MCP is an agent test harness with a separate wallet from Privy product wallets. Refund leftover agent-test USDC to Phantom when QA funding runs finish.
- Milestone product work merges to integration branches (`milestone-1`, `milestone-2`, …, or lanes like `platform-balance`); start each milestone branch from the previous milestone branch, not `main`. Post-M5 lanes are separate milestones for treasury yield accrual and in-platform agentic trading (strategy agents emit intents; backend Privy-signs; no external bot custody).
- Do not track `.cursor/hooks` in git; local Cursor hook state stays gitignored.
- Product uses Solana mainnet (not devnet) for RPC, USDC, and chain operations.
- M0 only needs `DATABASE_URL`; M1+ needs Privy app id/secret/client id; M2+ also needs `PRIVY_AUTHORIZATION_PRIVATE_KEY`, `PRIVY_AUTHORIZATION_KEY_ID` (Privy dashboard quorum id, not derivable from the private key), `RELAYER_PRIVATE_KEY`, and RPC. M2 Privy sweeps use one app authorization keypair in env; member wallet create must set `owner` plus `additional_signers` with that quorum id at create time; treasuries are app-owned. iOS bundle `com.monaco.app` must be on the Privy iOS client or OTP `sendCode` returns 403 `invalid_native_app_id`. Pre-fix wallets without signers need one-time recreate or owner-signed update — not OTP PATCH as the product path. Backend startup fails if relayer fee payer holds ≤0.001 SOL on mainnet; relayer is app-owned in `.env.local`, not Privy (pubkey in README).
- M2+ money movement uses Deposit, Withdrawal, Transaction, and Position domain tables—not `sweep_tx_log` or `share_ledger`. M3 adds Jupiter Swap API v2 on mainnet (backend-only; treasury signs with app-owned Privy wallet + `PRIVY_AUTHORIZATION_*`). `transactions` rows track swaps, idempotent on `tx_signature` / `execute_request_id`; xStocks mints resolve via `api.xstocks.fi` public assets API.
- Group treasury value is total across USDC and all tokenized stock holdings, not cash alone; propose-buy amount cannot exceed treasury total.
